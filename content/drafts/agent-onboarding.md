---
title: Documenting your docs for agents
date: 2026-05-09
---

I've kept a style guide of some sort for my tech writing teams since I started doing this back in the 1900s. It used to be a Word doc buried on the intranet (remember those?) where it would be largely unread and ignored. Then they went to the web or an internal wiki. They are absolutely imperative and I can go on for hours about the care and feeding of a living document like a style guide. But the recent challenge has been how to get agents to read the thing and use it. And this quest uncovered a much bigger revelation: the solution to this is how you can keep _everything_ up to date.

OK, jump back five or ten years. You create a style guide in Confluence or whatever your company uses for internal docs. It's an A-Z list of words you should or shouldn't use, maybe some branded terms to outline what your company has trademarked, and maybe special terms lists like inclusive language or American spellings. You then define a process on how words are added or changed. Style guides aren't a democracy, and they're very perishable, so you probably have some monthly meeting where people argue about why marketing wants to capitalize the word Template and if you need to actually do that. And you edit the Confluence pages with their wonderful text editor and they're completely out of date in about five minutes. And nobody can find them, because when you search Confluence for "style guide" it returns a ten-year-old page about CSS templates written by someone who left the company nine years ago.

Handbook pages are the same thing. I'm a big proponent of having an internal handbook where any institutional knowledge is captured. I want to be able to point every writer on the team to something that tells them how we name images or apply bold to words or write warnings or review docs. Any "how do I..." question should be in that guide. I've used Confluence for this, and it works, but has the same problems. Any time I hire a new writer, the moment the offer is signed, I have a new task: go to the handbook and see how far it has drifted from reality. And when they start, I inevitably have a slew of valid questions, usually along the lines of "this Confluence page says install Node v17 and this one says install Node v22."

In the last year, another major issue has emerged: Confluence pages aren't that machine-readable. Atlassian does have an MCP server now, but in the current rush of AgentMania, there were multiple groups in my company scraping the style guide pages, throwing them in an agent, and calling it a day. Agents _should_ be looking at the style guide, but they need the latest style guide, and it needs to be in a format their LLM brains can best understand. The immediate thought was I had to move these pages somewhere else, maybe an internal web site or something with an MCP server others could use. That went up and down the flagpole several times, but after a certain point in a company's maturity, starting a new web site suddenly becomes like building high-speed rail in America, and you start wondering if throwing the thing on a hidden GeoCities web site would be Career-Limiting Behavior.

A few things quickly lined up here. First, Claude and the Atlassian connector got really good at not only pulling pages from Confluence, but publishing Markdown files from a GitHub repo to a Confluence page without any bizarro iframe nonsense or other dramatics. Tell Claude to push a .md into a Confluence directory, and the results look 97% like a human wrote the page from scratch. Also, the landscape of how agents find onboarding instructions has radically evolved. I work with a guy named Tristan Denyer and we talk about this every day, but [he wrote an excellent article](https://www.tristandenyer.com/work/ai-agent-persistent-memory-knowledge-system) about how his team does this, and you can too. I stole a subset of his idea and here's what it looks like in broad strokes.

1. We're docs-as-code, so the docs are in a GitHub repo.
2. The repo has a `CLAUDE.md` in the root directory. which is the tip of the iceberg. This is akin to the onboarding doc you'd give a new engineer, telling them the rules of the road for developing anything in the repo.
3. Scrape those style guide pages out of Confluence for the last time, and put them in `.claude/docs/style-guide`. While you're at it, break out that handbook and put those pages under `.claude/docs/handbook`.
4. In the `CLAUDE.md`, you say, "Hey, we have a style guide here. Pay attention to that."
5. Write a `.claude/skills/style-guide/SKILL.md` that defines how to check a page with the style guide, how to ask questions like "hey style guide, do you hit or push keys?", and how to push the style guide pages back to Confluence.
6. Also put in your `CLAUDE.md` instructions saying that if you're an agent and you change some functionality in the docs site, make sure to update the `CLAUDE.md` _and also update the handbook_.

Read that last line over again. Yes, this works. When you tear apart your site with Claude and change the front matter from `search_keywords` to `keywords` for whatever reason, Claude will not only implement the code, but it will go to your handbook page on how to write Markdown and change the section on front matter, updating the term. You won't have a page that has the wrong variable listed, and not find it until something breaks.

Suddenly, there's a bunch of behavior that changes when you're using Claude in your repo:
 * When you make code changes with an agent, they're automatically reflected in your handbook.
 * Agents are automatically reading the handbook, so their future work is using the most up-to-date knowledge.
 * Humans who need a quick answer will have an up-to-date handbook. They can also quickly ask Claude things like "what front matter do I need in a new topic?"
 * You can write skills that suddenly know everything in your handbook. Write a skill to audit topics, and it knows your style guide. Write a topic to deal with image files, and it knows your naming scheme. Write a topic to add a bunch of redirects, and it knows where your SSG keeps them.
 * Every step of a complicated handbook topic will be performed. A great example: I have a handbook page on how to move and delete topics. When a human does this, there are a bunch of things they have to remember: you edit a TOC; you may or may not have to edit a second TOC for the previous version of the product; you need redirects; you have to fix links in other pages; you have to delete the files from Git. There's a handbook page explaining this. Or tell Claude "hey remove the 'About ABC Penguin' from the docs" and it will just do those five things." (Yes, it's technically possible to mess things up. That's why we use Git, right?)

Here's an absolutely crazy one that happened this week. We use [Fern](https://buildwithfern.com) for our docs. Fern has the concept of versions: you can have docs for v1, v2, v3 and so on. As a writer, you have to know where to put files, how to change config, how the TOCs are defined for different versions, and how the behavior of this works in production. It's not the same as Jekyll or Gatsby or a home-rolled solution. That's a handbook page I haven't written since we switched to Fern, and after a few questions on how to do this, it was time to write the handbook page. But _I_ didn't write it. I told Claude, "Hey, look at the code, then look at Fern's docs, then look at our TOCs, and sing me the song of your people over in `.claude/docs/handbook/versioning.md`." And... it did. Is it a perfectly-crafted Raymond Carver short story? No. Does it capture the facts in a way that man and machine can read? Sure. Will it get updated when I roll out the next version of the docs or Fern changes how the config works? Yes it will.

If you've gotten this far, you're probably wondering when I'm going to share all my skills and prompts and examples. And of course I did this at work in a private repo and I can't. Here's the beautiful thing: you can learn this the same way I did. Just ask Claude. "Hey Claude, what's the best practice for writing a skill to mirror my style guide back to Confluence using the Atlassian connector?" Does it run slow? Ask Claude how to make it run faster. (I now build the style guide into a lean binary tree it can read easier than looking at 17 Markdown pages.) It's called _meta-prompting_. Use AI to write your prompts for AI.

And once you get this rolling, you can institute a culture of always asking Claude when you have a question. Sure, I can probably rip through the A-Z list in VSC to find the exact hit of a word, and I do. But for fuzzy searching, _just ask Claude_.
